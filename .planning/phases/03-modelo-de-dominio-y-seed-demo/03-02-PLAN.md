<threat_model>
**Defensas declaradas en este plan:**

1. **Gate DEMO_MODE dentro del service (PITFALL 4 + Security "contraseñas de seed/demo en prod"):** `seed_if_demo_mode` retorna None sin tocar la BD cuando `settings.DEMO_MODE=False`. El gate vive DENTRO del service (no confiar solo en el caller del lifespan) — defense-in-depth. En producción DEMO_MODE=false (default del .env.example), así que las contraseñas Demo!1234 NUNCA se insertan en prod. **Verificación:** `test_demo_mode_false_no_siembra` (monkeypatch False → 0 filas nuevas).

2. **Idempotencia por natural-key get-or-create (PITFALL 3 + PITFALLS "Looks Done But Isn't" seed check):** cada entidad (restaurante, usuario, mesa, categoría, producto) se busca por su natural key ANTES de insertar. Reiniciar el contenedor N veces deja exactamente el mismo estado. Si se usara INSERT ciego, cada restart duplicaría filas o rompería el boot con IntegrityError. **Verificación:** `test_seed_idempotente` (counts idénticos tras 2 pasadas) + `test_seed_idempotente_tras_usuarios_ya_existentes` (caso edge de restart real) + verify_seed.sh sección 6-7 (restart del api + comparación de counts).

3. **Atomicidad del seed (anti-Pitfall 6):** un solo `await session.commit()` al final de seed_demo. Si algo falla a mitad (p.ej. IntegrityError por typo), la transacción completa se revierte — no queda un restaurante sin menú ni mesas sin restaurante. `flush()` intermedio asigna ids sin commit para que los FKs dentro de la tx funcionen.

4. **Snapshot de precio en el seed:** los productos se crean con precios Decimal exactos (no floats ni ints en strings). El seed no genera pedidos demo (eso sería Phase 6+) — solo productos y mesas, dejando el dominio listo para que un usuario real o un cliente demo haga el primer pedido.

5. **Anti-timing en creación de usuarios:** emails lowercased + stripped antes del SELECT (mismo patrón que admin_service.py Phase 2) — un usuario pre-existente con mayúsculas no causa duplicado.

6. **Restaurante demo con activo=True** (default): aparece en `list_restaurantes` de Phase 2 (que filtra solo activos). Phase 5 (cliente descubriendo restaurantes) lo verá sin configuración extra.

**Amenazas NO cubiertas (por diseño o scope):**
- **No se generan pedidos/reservas/sesiones/pagos demo:** el seed deja el dominio en estado "restaurante recién abierto, sin actividad". Generar pedidos demo falsos complica la semántica (qué usuario, qué mesa, qué estado) sin valor para Phase 4-5. Si Phase 8 quiere datos históricos para reportes, será un seed extendido propio.
- **Contraseñas demo iguales para todos (Demo!1234):** simplicidad deliberada. Si el security audit lo pide, rotación fácil en una constante. En prod DEMO_MODE=false las excluye.
- **QR estable (no efímero):** decisión locked (ARCHITECTURE Pattern 4). Token efímero/rotativo es v2 (OPER-04).
