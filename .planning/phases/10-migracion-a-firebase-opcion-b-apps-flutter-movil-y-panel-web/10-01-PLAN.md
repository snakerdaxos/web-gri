<threat_model>
- **Claims inmutables client-side:** ningún client puede escribir sus propios claims (solo Admin SDK). Las rules NUNCA aceptan role desde request.resource.data — solo request.auth.token.
- **Doc usuarios espejo no autoriza:** prohibido cualquier get(/usuarios/...) en rules para authz (costo access-call + desync). La rules solo lo tocan para forzar role:'cliente' en create de auto-registro y congelar role/restauranteId en update (hasOnly(['nombre'])).
- **Presupuesto access-calls (10 por doc, 20 por multi-doc/tx):** los gets por match ya están contados: sesiones create 1, pedidos create 3, reservas create 1, calificaciones create 3. NO agregar más gets "por seguridad".
- **IDs deterministas = anti colisión:** reservas/{mesaId}_{fecha}_{HH} y sesiones/{mesaId} restauran los UNIQUE de MySQL; set() sobre doc existente se evalúa como UPDATE en rules (no como create) — el "re-abrir sesión" queda bloqueado ex profeso.
- **serviceAccountKey gitignored:** el seed contra el proyecto real la requiere; NUNCA al repo. Emuladores no necesitan credenciales.
- **Emuladores por flag:** las apps solo conectan a emuladores con --dart-define=USE_EMULATORS=true (planes 10-02+); este plan no toca apps.
- **Sin backend no hay validación fuerte de totales (gap estructural aceptado):** rules validan estructura (items list 1..50, total >= 0 num, restauranteId consistente con la mesa); snapshot precio/nombre embebido por item; validación de montos fuerte = Functions (fase pagos, DEFERRED).
</threat_model>
