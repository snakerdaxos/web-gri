<threat_model>
T-04-01 (CORS wildcard leak): `allow_origins=["*"]` + `allow_credentials=True` es inválido
(FastAPI lo rechaza en runtime). Mitigación: origins EXPLÍCITOS (`http://localhost:5173`)
via `CORS_ORIGINS` (config dotenv), lista parseada por split(","). Prod (Phase 9) pone
el dominio HTTPS del panel. Nunca wildcard.

T-04-02 (Tenant isolation bypass en /staff): si staff_service olvida filtrar por
scope.restaurant_id y confía en el query param `restaurante_id`, un admin de restaurante A
podría leer mesas/stats de restaurante B. Mitigación: helper `_resolve_rid(scope, restaurante_id)`
que (a) para staff SIEMPRE retorna `scope.restaurant_id` (ignora el param), (b) para
super_admin valida que el restaurante exista y esté activo (404 otherwise). El query param
es HINT para super_admin, NUNCA fuente de verdad para staff. Tests de acceso cruzado lo prueban.

T-04-03 (IDOR via restaurante_id de super_admin): un staff que envíe `?restaurante_id=999`
no debe recibir datos de otro tenant. Cubierto por T-04-02 (param ignorado para staff).

T-04-04 (Count query DoS): COUNT(*) sin WHERE restaurant_id en restaurante grande filtra
toda la tabla. Mitigación: siempre `where(Pedido.restaurant_id == rid)` y `where(Reserva.fecha == func.curdate())`,
aprovechando los indexes compuestos existentes (`ix_pedido_restaurante_estado`,
`ix_reserva_restaurante_fecha_estado`). Pitfall 6 del research: usar `func.curdate()` (DB-side
Bogota TZ), NO `date.today()` (container TZ).
</threat_model>
