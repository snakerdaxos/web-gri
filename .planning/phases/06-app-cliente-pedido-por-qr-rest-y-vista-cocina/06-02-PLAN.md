API (base URL Env.apiBaseUrl, auth Bearer via ApiClient):
- POST /cliente/sesiones {"codigo_qr": "GRI-MESA-001"} → 201|200 SesionRead | 404 | 409 (detail describe el caso)
- GET /cliente/sesiones/actual → 200 SesionRead | 404 sin sesión
- POST /cliente/sesiones/actual/cuenta → 200 SesionRead (solicita_cuenta=true) | 404
- POST /cliente/pedidos {"sesion_id": int|null, "items": [{"producto_id": int, "cantidad": int}], "notas": str|null} → 201 PedidoRead | 404/409/422
- GET /cliente/pedidos/actual → 200 list[PedidoRead] (newest first, todos los estados) | 404

SesionRead JSON: {id, restaurante_id, restaurante_nombre, mesa_id, mesa_numero, abierta_en, solicita_cuenta, solicitada_en}
PedidoRead JSON: {id, sesion_id, mesa_numero, estado, total (float), notas, created_at, items: [{producto_id, nombre, cantidad, precio_unitario (float), subtotal (float)}]}
estado ∈ {enviado, aceptado, en_preparacion, servido, rechazado}

<threat_model>
UI-side (mitigaciones server-side ya verificadas en 06-01):
1. **Input manual validado**: formato GRI-MESA-XXX con validación pre-red en el TextField (regex GRI-MESA-\d{3}); errores del server (404/409) → SnackBar rojo con detail — nunca crash.
2. **Cámara no requerida**: MobileScanner se monta solo tras tap "Escanear con cámara"; input manual SIEMPRE visible (widget tests + entornos sin secure context/CDN lo necesitan — Pitfall 5/9 research).
3. **Doble disparo**: scanner hace controller.stop() tras primer hit + flag _navigating; botón "Enviar pedido" disabled mientras vuela el request (Pitfall 4).
4. **Total display**: el total mostrado antes de enviar es informativo; el server responde el total real — la UI re-renderiza con la respuesta.
5. **Agotado visible desde el inicio**: productos con disponible=false se muestran deshabilitados con "Agotado" (el 409 del POST es red de seguridad, no UX — Pitfall 7).
</threat_model>
