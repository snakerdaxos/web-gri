<threat_model>
**Amenazas que este plan mitiga (referencia VALIDATION.md T-02-02, T-02-03, T-02-04):**

1. **Cross-tenant data leak (AUTH-04, highest risk)** → Mitigación: `TenantScope` dependency es el ÚNICO punto que derivar el filtro; `admin_service.get_restaurante_for_staff` aplica `.where(Restaurante.id == scope.restaurant_id)` cuando no es super_admin; cross-tenant retorna None → router devuelve **404 (no 403)** para no revelar existencia. Test hard gate: `test_staff_cross_tenant_404` (Pitfall 3 del research).
2. **Role escalation (AUTH-03)** → Mitigación: `require_roles(*allowed)` factory gate en cada endpoint admin; cliente sin privilegios recibe 403; sin token recibe 401. Matriz del research Pattern 4 respetada.
3. **Staff misconfigured (NULL restaurant_id)** → Mitigación: `get_tenant_scope` lanza 403 "Staff sin restaurante asignado" si el user es staff pero restaurant_id is None. Previene queries con filtro NULL que matchearían todo.
4. **PLAT-03 privilege: crear super_admin vía staff endpoint** → Mitigación: `StaffCreate.role` enum restringe a los 3 roles staff (admin_restaurante, mesero, cocina). Intentar role=cliente o super_admin → 422. Nadie puede escalar a super_admin vía API (solo el bootstrap del lifespan puede crearlo).
5. **PLAT-03 FK inválido: staff para restaurante inexistente** → Mitigación: `create_staff` hace `session.get(Restaurante, restaurante_id)` primero; si None → 404 antes de insertar el usuario.
6. **password_hash leak en StaffRead** → Mitigación: `StaffRead` Pydantic sin `password_hash` (igual que UserRead en Plan 02-01).
7. **Restaurante inactivo accesible** → Mitigación: `get_restaurante_for_staff` filtra `Restaurante.activo.is_(True)` (super_admin tampoco ve inactivos por esta vía; el list para super_admin en `list_restaurantes` puede mostrar todos — decisión: en este phase list_restaurantes filtra solo activos también, para consistencia; super_admin gestión de inactivos es Phase 8 PLAT-05).
</threat_model>
