<threat_model>
1. **Concurrencia de reservas (RESV-02 — PITFALLS P1, la trampa crítica):** check-then-insert pierde la carrera. Mitigación: migración 0003 `UNIQUE (mesa_id, fecha, hora_inicio)` + `select(Mesa).with_for_update()` + `except IntegrityError → 409`. Verificado por test_reserva_concurrency.py (10 POSTs concurrentes → 1×201 + 9×409).
2. **get_tenant_scope REJECTS cliente (403):** /cliente/* DEBE usar `Depends(require_roles(RolUsuario.cliente))` (que internamente usa get_current_user). NUNCA get_tenant_scope — sino todo /cliente/* da 403. El "tenant" del cliente se deriva de reserva.usuario_id, no del token.
3. **Existence hiding cross-user (RESV-04 cancelar):** al cancelar, si `reserva.usuario_id != current_user.id` → 404 (NO 403). Misma convención que AUTH-04 cross-tenant: nunca revelar existencia de reservas ajenas.
4. **Capacidad de mesa (RESV-01):** el SELECT de mesas candidatas filtra `Mesa.capacidad >= body.num_personas`. Si ninguna mesa alcanza → 409 "No hay mesas con capacidad suficiente".
5. **Validación de fechas pasadas (RESV-01/04):** `body.fecha < date.today()` → 400 al crear; `reserva.fecha < date.today()` → 400 al cancelar (no se cancelan reservas pasadas). TZ America/Bogota sin DST — seguro.
6. **Decimal serialization (Pitfall 3):** Producto.precio es Numeric(10,2) → asyncmy devuelve Decimal → Pydantic v2 lo serializa como JSON string por defecto → el cliente Dart espera double. Fix: `precio: float` + `@field_serializer("precio")` que coerce `float(v)` en schemas/menu.py. Test test_precio_is_float lo verifica.
7. **Transaccionalidad mesa+reserva:** la mutación de estado de mesa (disponible→reservada) y el INSERT de reserva DEBEN estar en la misma transacción. Si el INSERT falla, la mesa no queda trabada en reservada.
8. **Auto-confirm locked:** reserva nace en `estado=confirmada` (decisión del usuario — sin aprobación manual). El estado `pendiente` existe en la máquina pero NO se usa en Phase 5.
</threat_model>
