<threat_model>
1. **Tenant isolation staff (RESV-05 — AUTH-04):** GET /staff/reservas DEBE filtrar por `_resolve_rid(scope, restaurante_id)` — nunca por el param crudo. Un staff de tenant A con `?restaurante_id=B` obtiene sus propias reservas (param ignorado, T-04-02); super_admin sin param → 400. Cross-tenant lectura estructuralmente imposible.
2. **MESA_TRANSITIONS autoritativa (MESA-04):** POST /staff/mesas/{id}/estado DEBE llamar `validar_transicion("mesa", actual, nueva)` antes de mutar. Transición inválida (ej. limpieza→ocupada) → `TransicionInvalidaError` → router catch → 409. NUNCA inline `if estado == ...`.
3. **Existence hiding cross-tenant (mesa):** POST /staff/mesas/{id}/estado sobre mesa de otro tenant → la query filtra por rid resuelto → mesa no encontrada → 404 (NO 403, NO 200). Mismo principio que AUTH-04.
4. **super_admin restaurante_id validation:** super_admin DEBE pasar `?restaurante_id=` (400 si falta) y debe apuntar a restaurante activo (404 si no). Reutiliza `_resolve_rid` existente — no reimplementar.
5. **Fecha default DB-side (Pitfall 6 TZ):** GET /staff/reservas sin `?fecha=` → default `func.curdate()` (NO `date.today()` Python — skew de TZ). Misma decisión que Phase 4 `reservas_hoy`.
</threat_model>
