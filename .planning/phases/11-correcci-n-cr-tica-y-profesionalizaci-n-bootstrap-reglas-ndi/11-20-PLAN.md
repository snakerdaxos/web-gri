<!-- LA RESTRICCION DURA DEL PLAN. No negociable. -->
El script **importa** estas tres piezas y no reimplementa nada de lo que hacen:

| Módulo | Qué aporta | Por qué se reutiliza |
|---|---|---|
| `functions/src/auth-matrix.js` | `autorizarAlta({callerRole, callerRid, rolPedido, ridPedido})` y `ROLES_ASIGNABLES` | Decide quién puede crear a quién y con qué rid. Ya tiene la combinatoria completa de escalada |
| `functions/src/baja-matrix.js` | `autorizarCambioEstado({callerRole, callerRid, callerUid, objetivoRole, objetivoRid, objetivoUid})` | Decide la baja/readmisión, con las dos prohibiciones (nadie toca a un `super_admin`, nadie se toca a sí mismo) |
| `functions/src/password-policy.js` | `validarPassword(password)` | La misma política que aplicaría el servidor |

Las tres son **puras**: cero imports de `firebase-admin` o `firebase-functions` (verificado). Por eso
se pueden importar desde `scripts/`, que es otro paquete, sin arrastrar dependencias ni duplicar
`node_modules`. Ambos directorios son `"type": "module"`, así que el import relativo
`../functions/src/auth-matrix.js` funciona tal cual. **Si alguna de las tres dejara de ser pura, este
plan se rompe**: por eso la Tarea 3 incluye un gate que lo comprueba.

**Cómo se resuelve "quién llama" sin un token.** Las callables sacaban el rol del llamador de
`request.auth.token`. Aquí no hay token, así que el actor se pasa explícitamente:
`--como <email>`, y el script resuelve sus claims reales con `getUserByEmail(...).customClaims`.
Esos claims son los que se le pasan a la matriz. Es **obligatorio**, no opcional ni con valor por
defecto: sin actor no se evalúa autorización, y un script que no evalúa autorización es justo lo que
este plan existe para evitar. Si el actor no tiene claims o no existe → error claro y salida 1.

**Comandos:**
```
node scripts/gestion_staff.mjs listar   --como <email> [--rid <slug>]
node scripts/gestion_staff.mjs crear    --como <email> --email <nuevo> --nombre "..." --rol <admin_restaurante|mesero|cocina> [--rid <slug>] [--password <...>]
node scripts/gestion_staff.mjs baja     --como <email> --uid <uid>   (o --email-objetivo)
node scripts/gestion_staff.mjs reactivar --como <email> --uid <uid>
node scripts/gestion_staff.mjs promover-super --email <cuenta> --confirmo-promover-super
```
Las cuatro primeras reproducen paso a paso lo que hacen `crear-usuario-staff.js` y
`cambiar-estado-staff.js`: misma secuencia, mismos efectos, mismos mensajes de error. Leerlas y
seguirlas literalmente es parte del trabajo — no inventar una secuencia nueva.

**`promover-super` va en el MISMO script, y es deliberado.** Razones: (a) concentra en un solo archivo
el manejo de la clave de servicio, en vez de repartirlo; (b) es la única vía de recuperación si el
propietario pierde su cuenta de `super_admin`, y esconderla en otro sitio la hace inencontrable el día
que haga falta. Va con nombre de comando distinto y bandera explícita
`--confirmo-promover-super` porque **no pasa por `autorizarAlta`**: esa matriz prohíbe asignar
`super_admin` a propósito, y saltársela es exactamente lo que este comando hace. Debe imprimir un
aviso destacado, pedir confirmación interactiva además de la bandera, y registrar la operación.
El bootstrap del primer super_admin ya no hace falta en la práctica (el propietario ya lo es), pero
esta es su red de seguridad.

**Clave de servicio:** `p-gri-b5b40-firebase-adminsdk.json` en la raíz del repo, **gitignored**
(verificado: `.gitignore:36` con el patrón `*firebase-adminsdk*.json`). El script la referencia por
RUTA vía `GOOGLE_APPLICATION_CREDENTIALS` o `--key <ruta>`; **jamás** lee su contenido para mostrarlo,
ni lo vuelca en logs, ni lo incluye en mensajes de error. Si falta, mensaje accionable y salida 1.

**Precedente de estilo:** `scripts/seed_firebase.mjs` ya inicializa el Admin SDK con credenciales por
defecto o clave, y es idempotente por clave natural. Seguir ese patrón; no inventar otro.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operador con la clave de servicio → Firebase Auth | El Admin SDK salta las rules por completo: quien ejecuta el script es omnipotente |
| script → matrices puras | Si el script decidiera por su cuenta, las 149 pruebas dejarían de proteger lo ejecutado |
| clave de servicio → repositorio | Un commit accidental de la clave comprometería el proyecto entero |
