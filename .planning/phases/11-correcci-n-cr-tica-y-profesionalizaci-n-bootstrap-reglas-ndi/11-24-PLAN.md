<!-- Decisión BLOQUEADA. No re-abrir: desactivar, nunca borrar. -->

**Qué significa "desactivar":**
1. `auth.updateUser(uid, { disabled: true })` — no puede iniciar sesión.
2. `auth.setCustomUserClaims(uid, null)` — pierde `{role, rid}`, así que aunque conservara un token
   vivo, `firestore.rules` deja de tratarlo como staff (sin claim `role` se evalúa como cliente).
3. `auth.revokeRefreshTokens(uid)` — invalida los refresh tokens para que no pueda renovar.
4. El doc espejo `usuarios/{uid}` se marca `activo: false` con `desactivadoAt` y `desactivadoPor`,
   pero **conserva `role` y `restauranteId`**: son los que permiten reactivar y los que usan los
   reportes históricos.

**Reactivar** es la operación inversa: `disabled: false` y restaurar los claims **leyéndolos del doc
espejo** (`role` + `restauranteId`), que es justo por lo que el paso 4 no los borra. Documentarlo en
el código: si alguien "limpiara" esos campos al desactivar, la reactivación quedaría rota y no habría
forma de saber qué rol tenía.

⚠️ **Ventana residual conocida:** un ID token ya emitido vive hasta ~1 hora. Durante ese rato, la
persona desactivada conserva sus claims en el token en curso. `revokeRefreshTokens` impide renovarlo y
`disabled: true` impide volver a entrar, así que la ventana está acotada y no se puede extender. Es un
riesgo aceptado y documentado, no un olvido: cerrarlo del todo exigiría que las rules consultaran un
documento por request, lo que rompería el presupuesto de access-calls que documenta la cabecera de
`firestore.rules`.

**Matriz de autorización — la misma del alta, más dos prohibiciones nuevas:**

| Llamador | Puede desactivar/reactivar a |
|---|---|
| `super_admin` | staff de cualquier restaurante |
| `admin_restaurante` | **solo** staff de su propio `rid` |

Prohibiciones absolutas, cada una con su test de rotura:
1. **Nadie puede desactivar a un `super_admin`** por esta vía (ni otro super_admin).
2. **Nadie puede desactivarse a sí mismo** — dejaría el restaurante sin administrador, que es
   exactamente el escenario que la decisión de permitir dos `admin_restaurante` (plan 11-08) buscaba
   evitar.
Ambas se validan **en la callable**, no en el cliente, igual que el alta.

**Contrato de la callable:**
```
cambiarEstadoStaff({ uid: string, activo: boolean })
  → { uid, activo, rol, restauranteId }
```
Códigos de error, coherentes con los del alta (plan 11-08):
| Situación | Código |
|---|---|
| Sin sesión | `unauthenticated` |
| `uid` ausente o `activo` no booleano | `invalid-argument` |
| Llamador no es super_admin ni admin_restaurante | `permission-denied` |
| Objetivo es `super_admin` | `permission-denied` |
| Objetivo es el propio llamador | `permission-denied` |
| Objetivo de otro `rid` siendo admin_restaurante | `permission-denied` |
| El uid no existe en Auth | `not-found` |
| Fallo inesperado del Admin SDK | `internal` (mensaje genérico, nunca el stack) |

**Patrón a reutilizar:** `functions/src/auth-matrix.js` (plan 11-08) es lógica PURA sin imports de
firebase, con 27 casos que corren en 61 ms. Esta plan sigue el mismo patrón en un archivo hermano,
`baja-matrix.js`, en lugar de ampliar el existente: son decisiones distintas (una crea, otra revoca) y
mezclarlas haría la tabla de casos difícil de leer. Compartir solo las constantes de roles importándolas
de `auth-matrix.js`.

**Rules:** no cambian. El doc espejo lo escribe el Admin SDK, que las salta por diseño; y la lectura
del equipo por el admin ya se abrió en el plan 11-10, acotada a su `rid`.

**Fuera de alcance:** eliminar cuentas (explícitamente descartado por el usuario) y desactivar
clientes (esto es gestión de personal; un cliente no pertenece a ningún `rid`).
