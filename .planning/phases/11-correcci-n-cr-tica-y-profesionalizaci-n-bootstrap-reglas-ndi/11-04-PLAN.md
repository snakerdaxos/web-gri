<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| cliente autenticado → `usuarios/{uid}` | Punto de auto-ascenso: escribe su propio doc de perfil |
| staff tenant A → datos del tenant B | Aislamiento multi-tenant, enteramente delegado en las rules |
| cualquiera → colecciones sin `match` | Default deny de Firestore, hoy sin verificar |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-04-01 | Elevation of Privilege | auto-registro en `usuarios/{uid}` | mitigate | Casos `// ESCALADA` en `usuarios.test.mjs`: `role != 'cliente'` y `restauranteId != null` denegados; update de `role` propio denegado |
| T-11-04-02 | Elevation of Privilege | matriz rol × transición de `pedidos` | mitigate | Casos explícitos "mesero no puede aceptar" y "salto ilegal enviado→servido" |
| T-11-04-03 | Information Disclosure | lectura cruzada entre tenants | mitigate | Un caso `adminOtro → DENEGADO` por colección con datos de tenant |
| T-11-04-04 | Tampering | `restaurantes.califProm/califCount` escribible por cliente | accept | Gap estructural aceptado en v1 y documentado en `firestore.rules`; la validación fuerte vía Functions está DIFERIDA por decisión del usuario. El test fija el alcance exacto de lo permitido para que no se amplíe por accidente |
| T-11-04-05 | Elevation of Privilege | `plataforma/bootstrap` | mitigate | Test de default-deny desde todos los roles, escrito antes de que el documento exista |
</threat_model>
