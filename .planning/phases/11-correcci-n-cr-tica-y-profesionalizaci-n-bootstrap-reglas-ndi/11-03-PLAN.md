del panel (índice compuesto ausente)— y dejar detrás las dos redes de seguridad que faltaban.

estático que impide que este tipo de bug vuelva a llegar a producción.

Documentación oficial, textual:
"security rules are not filters — queries are all or nothing" · "Cloud Firestore evaluates a query
against its potential result set instead of the actual field values for all of your documents. If a
query could potentially return documents that the client does not have permission to read, the entire
request fails." · "Even if the user authored every story in the database, the query is rejected."
→ La query del menú del cliente está denegada DESDE EL DÍA UNO, incluso con el seed prístino donde
todo está activo. `CONCERNS.md` lo describe como un edge case: es incorrecto, es incondicional.

Reglas vigentes que la query debe replicar (`firestore.rules`):
```
match /categorias/{id} { allow read: if resource.data.activo == true || menuStaffOf(resource.data.restauranteId); }
match /productos/{id}  { allow read: if (resource.data.activo == true && resource.data.disponible == true)
                                       || menuStaffOf(resource.data.restauranteId); }
```
Regla mental permanente: **si la rule menciona `resource.data.X`, la query DEBE tener `where('X', …)`**.

Índices: varios filtros de IGUALDAD sobre campos distintos se resuelven con índices automáticos de
campo único. Solo hace falta índice compuesto con rangos (`<`, `<=`, `>`, `>=`) o con `orderBy` por
otro campo. Aplicado aquí:
| Query | ¿Compuesto? | Estado |
|---|---|---|
| `categorias` where `restauranteId` + `orderBy('orden')` (panel) | **SÍ** `(restauranteId ASC, orden ASC)` | ❌ FALTA |
| `categorias` where `restauranteId` + `activo` (cliente) | NO (solo igualdades) | ✅ nada |
| `productos` where `restauranteId` + `activo` + `disponible` (cliente) | NO (solo igualdades) | ✅ nada |
**Total de índices a añadir en esta fase: 1.**

⚠️ El emulador de Firestore **no valida índices compuestos**: "The Firestore emulator does not track
composite indexes and will instead execute any valid query." Ninguna suite local puede detectar el
bug del índice → el audit estático de la Tarea 3 es la ÚNICA mitigación automatizable. Está prohibido
dar el bug por cerrado apoyándose solo en tests de emulador.
