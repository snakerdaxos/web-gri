<!-- MATRIZ BLOQUEADA por el usuario (11-CONTEXT.md). No re-abrir, no "simplificar". -->

| Llamador | Puede crear usuarios de | Roles que puede asignar |
|---|---|---|
| `super_admin` | cualquier restaurante | `admin_restaurante`, `mesero`, `cocina` |
| `admin_restaurante` | **solo su propio** `rid` | `admin_restaurante`, `mesero`, `cocina` |

Resuelto por el usuario: SÍ, un `admin_restaurante` puede crear otro `admin_restaurante` acotado a su
propio rid (permite dos socios/gerentes y evita el bloqueo si esa única persona pierde el acceso).
Prohibiciones absolutas con test dedicado: (1) nadie asigna `super_admin`; (2) un `admin_restaurante`
nunca toca otro `rid`. Se valida EN LA FUNCIÓN, no en el cliente.

Como ambos llamadores asignan el mismo conjunto de roles y solo difieren en el `rid` efectivo, la
lógica se reduce a una decisión (`ridEfectivo`) y una prohibición de rol → **UNA sola callable**, no dos.

Lógica pura de referencia (`functions/src/auth-matrix.js`):
```javascript
export const ROLES_ASIGNABLES = ['admin_restaurante', 'mesero', 'cocina'];
export const ROLES_LLAMADORES = ['super_admin', 'admin_restaurante'];
export const SLUG_RE = /^[a-z0-9]+(-[a-z0-9]+)*$/;

export function autorizarAlta({ callerRole, callerRid, rolPedido, ridPedido }) {
  if (!ROLES_LLAMADORES.includes(callerRole))
    return { ok: false, code: 'permission-denied', msg: 'Solo super_admin o admin_restaurante pueden dar de alta staff.' };
  if (!ROLES_ASIGNABLES.includes(rolPedido))
    return { ok: false, code: 'invalid-argument', msg: `rol debe ser uno de: ${ROLES_ASIGNABLES.join(', ')}.` };
  if (callerRole === 'super_admin') {
    if (typeof ridPedido !== 'string' || !SLUG_RE.test(ridPedido))
      return { ok: false, code: 'invalid-argument', msg: 'restauranteId es obligatorio y debe ser un slug [a-z0-9-].' };
    return { ok: true, rid: ridPedido };
  }
  if (typeof callerRid !== 'string' || !callerRid)
    return { ok: false, code: 'failed-precondition', msg: 'Tu cuenta no tiene restaurante asignado.' };
  if (ridPedido !== undefined && ridPedido !== callerRid)
    return { ok: false, code: 'permission-denied', msg: 'No puedes crear usuarios de otro restaurante.' };
  return { ok: true, rid: callerRid };
}
```

Regla de códigos: `permission-denied` = "sé quién eres y no puedes"; `invalid-argument` = "lo que me
mandaste no tiene sentido". Nunca mezclarlos, y nunca revelar estado interno en el mensaje.

El Auth emulator emite tokens sin firmar que el Admin SDK y el emulador de Functions aceptan: es lo
que permite probar la matriz con tokens REALES portando claims reales.

Secuencia obligatoria:
1. `if (!request.auth) throw new HttpsError('unauthenticated', 'Debes iniciar sesión.')`.
2. Validar el payload `{email, password, nombre, rol, restauranteId?}`: email string con `@`,
   password string de longitud >= 8 (Firebase exige 6; el producto exige 8 y el formulario debe
   coincidir), nombre string no vacío. Errores → `invalid-argument`.
3. Llamar `autorizarAlta({ callerRole: request.auth.token.role, callerRid: request.auth.token.rid,
   rolPedido: rol, ridPedido: restauranteId })` y, si `!ok`, `throw new HttpsError(d.code, d.msg)`.
   **Toda la decisión de autorización vive aquí, no en el cliente.**
4. Comprobar que `restaurantes/{ridEfectivo}` existe → si no, `not-found` "El restaurante X no existe."
   (evita crear staff huérfano de un restaurante que nunca se creó).
5. Alta idempotente por correo, con el MISMO patrón que `scripts/seed_firebase.mjs`:
   `createUser({email, password, displayName: nombre.trim(), emailVerified: true})`; si lanza
   `auth/email-already-exists`, recuperar con `getUserByEmail` y aplicar el **anti-secuestro** con las
   TRES comprobaciones (las dos primeras protegen a otros tenants; la tercera protege a los clientes):
   - si los claims previos tienen `role === 'super_admin'` → `permission-denied` "Esa cuenta es de plataforma."
   - si `prev.rid` existe y difiere del rid efectivo → `already-exists` "Ese correo ya pertenece a otro restaurante."
   - si `prev.role` existe y es `'cliente'` → `already-exists` "Ese correo ya tiene una cuenta de cliente;
     pide a esa persona que use otro correo para su cuenta de trabajo."
     Sin esta tercera rama, cualquiera que conozca el correo de un cliente registrado en la app puede
     convertir su cuenta en staff de su restaurante sin consentimiento: el cliente sigue pudiendo
     entrar, pero de pronto es `mesero` de un restaurante ajeno y ve sus pedidos y sus mesas.
     Nota de implementación: un cliente auto-registrado normalmente NO tiene claim `role` (la ausencia
     de `role` se interpreta como cliente en `firestore.rules`), así que la comprobación por claims no
     basta — hay que consultar también el doc espejo `usuarios/{uid}` y tratar
     `role === 'cliente'` o `restauranteId === null` con doc existente como cuenta de cliente.
   Cualquier otro error del Admin SDK → `internal` con mensaje genérico y, como tercer argumento,
   solo `e.code`. **Nunca** devolver `e.message` completo ni el stack.
6. `setCustomUserClaims(uid, { role: rol, rid: ridEfectivo })`.
7. `db.doc('usuarios/${uid}').set({ nombre, email, role: rol, restauranteId: ridEfectivo,
   updatedAt: serverTimestamp(), ...(creado ? {createdAt: serverTimestamp()} : {}) }, { merge: true })`.
8. `logger.info('staff alta', { uid, rol, rid, por: request.auth.uid, creado })`.
9. Devolver `{ uid, creado, rol, restauranteId }`.

Documentar en la cabecera la NO-atomicidad entre Auth y Firestore: si falla entre el paso 6 y el 7,
el usuario queda con permisos pero invisible en la lista de equipo. La mitigación es que la función es
idempotente y re-ejecutable: repetir el alta con el mismo correo converge al mismo estado. Ese hecho
debe aparecer también en el copy de la UI del plan 11-10 ("volver a crear con el mismo correo repara
un alta incompleta").

Exportar desde `functions/index.js` junto a `bootstrapPlataforma`, manteniendo el `initializeApp()`
único en el módulo raíz.
