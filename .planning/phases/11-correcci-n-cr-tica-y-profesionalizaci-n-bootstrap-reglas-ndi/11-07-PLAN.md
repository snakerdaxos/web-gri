**Guarda atómica.** El Admin SDK expone `DocumentReference.create(data)`, que falla con `ALREADY_EXISTS`
(gRPC code 6) si el documento ya existe. Es una sola operación de servidor: dos invocaciones
concurrentes no pueden ganar las dos.
⚠️ **Orden obligatorio:** la guarda atómica `create()` va PRIMERO, antes de cualquier consulta de
comprobación. Si se pone una query "¿ya hay algún super_admin?" delante, esa query resuelve la carrera
por sí sola en el caso feliz y deja la rama `ALREADY_EXISTS` de `create()` inalcanzable — con lo que
los tests pasarían idénticos aunque la guarda atómica no existiera, que es exactamente lo que hay que
evitar. La comprobación secundaria va DESPUÉS y su papel es distinto: cubrir un proyecto sembrado
previamente con el seed, que tendría super_admin pero no centinela; si detecta uno, borra el centinela
que acaba de crear y falla.

**Autorización de la llamada — dos factores, no uno.** La función NO acepta uid ni email destino:
promueve al llamador autenticado. Sobre eso:
- `request.auth.token.email_verified === true` es obligatorio. Sin esto, el filtro por correo tiene
  entropía nula: el registro de email/contraseña está ABIERTO (lo usa la app cliente), así que
  cualquiera que adivine el correo del fundador puede registrarlo primero y hacerse `super_admin`.
- `BOOTSTRAP_SECRET` (variable de entorno, fijada en el despliegue) comparado contra
  `request.data.secreto` con **comparación de tiempo constante** (`crypto.timingSafeEqual` sobre
  buffers de igual longitud; comparar primero longitudes y usar un buffer de relleno para no filtrar
  la longitud por el tiempo de la propia comparación).
- `BOOTSTRAP_EMAIL` comparado contra el correo del llamador, normalizado a minúsculas y recortado.
- **Fail closed:** si falta `BOOTSTRAP_EMAIL` o `BOOTSTRAP_SECRET`, la función no promueve a nadie.

Contrato de la callable:
```
bootstrapPlataforma(data: { nombre: string, secreto: string })
  → { uid: string, creado: boolean, reparado: boolean }
```

Códigos de error (`HttpsError`, verificados en firebase-functions 7.3.2):
| Situación | Código |
|---|---|
| Sin sesión | `unauthenticated` |
| `BOOTSTRAP_EMAIL` o `BOOTSTRAP_SECRET` sin configurar | `failed-precondition` |
| `nombre` o `secreto` ausentes / vacíos | `invalid-argument` |
| Secreto incorrecto · correo no autorizado · `email_verified` falso · centinela de otro uid · ya existe un super_admin | `permission-denied` (mensaje IDÉNTICO en los cinco casos: no revelar cuál falló) |
| Fallo inesperado del Admin SDK | `internal` (mensaje genérico, NUNCA el stack) |

**Guard del router del panel — el flujo se rompe solo si no se toca.** El guard vigente
(`panel_admin/lib/app.dart:30-41`) es:
```dart
final loggedIn = ref.read(authStateChangesProvider).value != null;
final onLogin = state.matchedLocation == '/login';
if (!loggedIn) return onLogin ? null : '/login';
if (onLogin) return '/';
return null;
```
con `refreshListenable` disparando en cada evento de `authStateChanges`. Consecuencia: en cuanto
`createUserWithEmailAndPassword` completa, hay sesión, el router se re-evalúa y expulsa al usuario de
`/bootstrap` hacia `/` **con la callable todavía en vuelo** — y la reversión de la cuenta se queda sin
pantalla donde ejecutarse. `/bootstrap` debe ser alcanzable CON y SIN sesión.

**Propagación de claims.** `claimsProvider` es `keepAlive` y solo se recomputa cuando emite
`authStateChanges`; `getIdToken(true)` refresca el token pero NO genera un evento de auth, así que el
provider sigue devolviendo el valor cacheado (`role: 'cliente'`) y el nuevo super_admin aterriza sin
rol. Hay que hacer `ref.invalidate(claimsProvider)` después de la callable. Precedente EXACTO en el
repo: `panel_admin/lib/features/auth/login_controller.dart:76` hace `ref.invalidate(claimsProvider)`
justo antes de leerlo.

**Inyección de configuración en los emuladores.** El emulador de Functions carga `functions/.env` y
`functions/.env.{projectId}` **al arrancar**, antes de que exista el proceso de test: escribir un
`.env` desde un `before()` llega tarde. Los valores de test viven en `functions/.env.demo-gri`
(creado en el plan 11-01, commiteado, solo se aplica al proyecto `demo-gri`) y el test los conoce vía
`--set-env` del wrapper `scripts/run_emulators.mjs`.
