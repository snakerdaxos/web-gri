<!-- Requisitos mínimos EXIGIDOS por la decisión bloqueada del usuario (11-CONTEXT.md). -->
1. Comprobar la inexistencia de cualquier `super_admin` de forma ATÓMICA — prohibido "leer y luego escribir".
2. Dejar rastro auditable de la invocación.
3. Tests dedicados que verifiquen que una segunda llamada SIEMPRE falla, incluidas llamadas concurrentes.

Mecanismo atómico elegido (y por qué): el Admin SDK expone `DocumentReference.create(data)`, que falla
con `ALREADY_EXISTS` (gRPC code 6) si el documento ya existe. Es una sola operación servidor: dos
invocaciones concurrentes NO pueden ganar las dos. Una transacción read-then-write sería más código y
la misma garantía; un `set()` sería directamente incorrecto (sobrescribe).

Contrato de la callable:
```
bootstrapPlataforma(data: { nombre: string })
  → { uid: string, creado: boolean, reparado: boolean }
```
El correo y la contraseña NO viajan en `data`: el llamador ya está autenticado (creó su cuenta con el
SDK cliente) y la función lo PROMUEVE a él. Así el único uid que puede quedar como super_admin es el
del llamador autenticado, y no hay forma de "crear un super_admin ajeno".

Códigos de error (`HttpsError`, verificados en firebase-functions 7.3.2):
| Situación | Código |
|---|---|
| Sin sesión | `unauthenticated` |
| `BOOTSTRAP_EMAIL` no configurado en el despliegue | `failed-precondition` |
| El email del llamador no coincide con `BOOTSTRAP_EMAIL` | `permission-denied` |
| Ya existe un super_admin / el centinela existe con otro uid | `permission-denied` |
| `nombre` ausente o vacío | `invalid-argument` |
| Fallo inesperado del Admin SDK | `internal` (mensaje genérico, NUNCA el stack) |

Propagación de claims (Trampa verificada): `setCustomUserClaims` solo se refleja "the next time a new
ID token is issued". Aquí el orden natural resuelve el problema — la cuenta se crea, se promueve y
DESPUÉS el cliente hace `getIdToken(true)`. El `claimsProvider` del panel ya usa
`getIdTokenResult(true)` (force refresh): mantener ese `true`.

Estilo de logging: `logger` de `firebase-functions` (structured logging), nunca `console.log`.

Crear `functions/src/bootstrap-plataforma.js` exportando `bootstrapPlataforma`, un `onCall` de
`firebase-functions/https` con `{ region: 'us-central1', maxInstances: 3 }` (la misma región que
declara el cliente; un desajuste da un 404 opaco que en Web se disfraza de CORS).

Secuencia obligatoria:
1. `if (!request.auth) throw new HttpsError('unauthenticated', 'Debes iniciar sesión.')`.
2. Leer `process.env.BOOTSTRAP_EMAIL`. Si está vacío → `failed-precondition` con mensaje
   "La plataforma no tiene configurado el correo de inicialización." **Fail closed**: sin esa variable
   la función no hace nada. Es lo que cierra la ventana de escalada entre el despliegue y el bootstrap.
3. Comparar `request.auth.token.email` con `BOOTSTRAP_EMAIL` normalizando a minúsculas y recortando
   espacios. Si no coincide → `permission-denied` con mensaje genérico ("Este correo no está autorizado
   para inicializar la plataforma."). No revelar cuál es el correo esperado.
4. Validar `request.data?.nombre` (string no vacío) → si no, `invalid-argument`.
5. Comprobación secundaria barata (cinturón + tirantes): consultar
   `usuarios` con `where('role','==','super_admin').limit(1)`. Si devuelve algo → `permission-denied`
   "La plataforma ya fue inicializada." Cubre el caso de un proyecto sembrado antes con el seed, que
   no tendría centinela.
6. **Guarda atómica:** `await db.doc('plataforma/bootstrap').create({ uid, email, nombre,
   createdAt: FieldValue.serverTimestamp(), userAgent, ip })` donde `userAgent` e `ip` salen de
   `request.rawRequest.headers['user-agent']` y `request.rawRequest.ip` cuando existan (documentar que
   pueden faltar en el emulador). Envolver en try/catch: si el error tiene `code === 6` o
   `ALREADY_EXISTS`, leer el centinela y:
   - si `centinela.uid === request.auth.uid` → **camino de reparación**: continuar al paso 7 y devolver
     `{ creado: false, reparado: true }`. Esto cubre la no-atomicidad entre Firestore y Auth: si la
     primera llamada murió después de crear el centinela pero antes de escribir los claims, la MISMA
     persona puede reintentar y converger.
   - si es otro uid → `permission-denied` "La plataforma ya fue inicializada."
7. `await getAuth().setCustomUserClaims(uid, { role: 'super_admin', rid: null })` — exactamente la
   misma forma de claims que produce `scripts/seed_firebase.mjs:47` (el super_admin NO lleva rid).
8. `await db.doc('usuarios/${uid}').set({ nombre, email, role: 'super_admin', restauranteId: null,
   updatedAt: serverTimestamp(), createdAt: serverTimestamp() }, { merge: true })` — doc espejo.
   Las rules no permitirían este write desde un cliente; el Admin SDK las salta por diseño.
9. `logger.info('bootstrap plataforma', { uid, email, reparado })` y devolver el contrato.

Exportar la función desde `functions/index.js` (`export { bootstrapPlataforma } from './src/bootstrap-plataforma.js';`),
manteniendo el `initializeApp()` único del módulo raíz.

En `firestore.rules`, añadir un `match` explícito para el centinela, justo antes del cierre del bloque
`documents`:
```
// ---- plataforma (centinela de bootstrap) · 0 access-calls ----
// Solo el Admin SDK (que salta las rules) lo toca. Ningún cliente, ni siquiera
// el super_admin, debe poder leerlo ni borrarlo: borrarlo re-abriría el bootstrap.
match /plataforma/{doc} { allow read, write: if false; }
```
Los tests de default-deny de `scripts/test/rules/restaurantes.test.mjs` (plan 11-04) deben seguir
pasando tras este cambio.

Documentar en `docs/FIREBASE_SETUP.md` una sección "Inicializar una plataforma nueva": crear

cuenta. Incluir el aviso de que la variable debe fijarse ANTES del despliegue.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| internet → callable `bootstrapPlataforma` | Función desplegada e invocable por cualquiera que conozca su URL |
| Cloud Function → Firebase Auth (claims) | El Admin SDK puede conceder `super_admin`: es el privilegio máximo del sistema |
| Cloud Function → `plataforma/bootstrap` | Documento que decide si el bootstrap sigue abierto |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-07-01 | Elevation of Privilege | ventana entre el despliegue y el primer bootstrap | mitigate | Triple cierre: (a) exige `request.auth` — el llamador debe tener cuenta; (b) exige que su correo coincida con `BOOTSTRAP_EMAIL`, fijado en el despliegue; (c) **fail closed** si esa variable no está definida. Sin la variable la función no promueve a nadie |
| T-11-07-02 | Elevation of Privilege | segunda invocación / carrera | mitigate | `DocumentReference.create()` como guarda atómica de una sola operación. Test de 5 invocaciones concurrentes que exige exactamente 1 ganador |
| T-11-07-03 | Elevation of Privilege | promoción de un uid ajeno | mitigate | La función SOLO promueve `request.auth.uid`; el payload no acepta email ni uid destino |
| T-11-07-04 | Tampering | borrado del centinela para re-abrir el bootstrap | mitigate | `match /plataforma/{doc} { allow read, write: if false; }` + comprobación secundaria de que no exista ya un `usuarios` con `role: 'super_admin'` |
| T-11-07-05 | Repudiation | quién inicializó la plataforma | mitigate | El centinela guarda uid, email, `createdAt` de servidor, user-agent e IP; `logger.info` estructurado en Cloud Logging |
| T-11-07-06 | Information Disclosure | mensajes de error | mitigate | Mensajes genéricos hacia el cliente; nunca se revela el `BOOTSTRAP_EMAIL` esperado ni el stack del Admin SDK |
| T-11-07-07 | Denial of Service | invocación masiva de la callable | mitigate | `maxInstances: 3`. App Check daría defensa real y queda documentado como deuda de seguridad conocida (DIFERIDO) |
| T-11-07-08 | Tampering | cuenta huérfana si la callable falla tras crear el usuario | mitigate | Reversión en el cliente (`currentUser.delete()`) + camino de reparación idempotente en la función para el mismo uid |
</threat_model>
