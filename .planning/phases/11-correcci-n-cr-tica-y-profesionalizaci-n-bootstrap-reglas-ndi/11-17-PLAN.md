- Falta el **Web client ID** (`703827387403-….apps.googleusercontent.com`): hace de `serverClientId`

**Paquete (VERIFICADO en la API de pub.dev el 2026-08-19):** `google_sign_in` **7.2.0**, publisher
verificado `flutter.dev`, publicado 2025-09-17. Requiere Flutter >= 3.29 (el repo tiene 3.47) y
Dart sdk `^3.7.0`. Dependencias de plataforma: `google_sign_in_android ^7.1.0`, `google_sign_in_ios ^6.2.0`,
`google_sign_in_web ^1.1.0`.

⚠️ **La API cambió por completo en 7.x. No usar la de 6.x** (`GoogleSignIn()` + `signIn()` +
`authentication.accessToken` ya no existen). La forma actual:
```dart
final signIn = GoogleSignIn.instance;
await signIn.initialize(clientId: <web client id en Web>, serverClientId: <web client id en Android>);
// Reanudar sesión sin interacción:
await signIn.attemptLightweightAuthentication();
// Interactivo (lanza si el usuario cancela; NO devuelve null):
if (signIn.supportsAuthenticate()) {
  final GoogleSignInAccount cuenta = await signIn.authenticate();
  final String? idToken = cuenta.authentication.idToken;
}
// Eventos: signIn.authenticationEvents.listen(...)
```
`authenticate()` **no está soportado en Web** (`supportsAuthenticate()` devuelve false): en web hay
que usar el botón renderizado del plugin o, más simple y sin dependencias nuevas de UI,
`FirebaseAuth.instance.signInWithPopup(GoogleAuthProvider())`, que `firebase_auth` 6.5.7 ya soporta.
**Esa es la rama elegida para Web.** En Android/iOS se usa `google_sign_in` 7.x + el `idToken` →
`GoogleAuthProvider.credential(idToken: idToken)` → `signInWithCredential`.
En 7.x `GoogleSignInAuthentication` expone **solo `idToken`** (los access tokens salen del
`authorizationClient`, que aquí no hace falta: Firebase solo necesita el idToken).

**Regla de `usuarios/{uid}` — comprobada, NO hay que tocarla:**
```
allow create: if signedIn() && request.auth.uid == uid
              && request.resource.data.role == 'cliente'
              && request.resource.data.restauranteId == null;
```
Un usuario de Google cumple los tres requisitos igual que un auto-registro: está autenticado, escribe
su propio uid y declara `role: 'cliente'` con `restauranteId: null`. Un usuario de Google **no obtiene
claims** — su `role` efectivo es "cliente" por ausencia de claim, exactamente como el registro actual.
El precedente de escritura del espejo está en `auth_controller.dart:123-165` (`RegisterController.submit`).

**Colisión de cuentas:** si el correo ya existe con email/contraseña, Firebase lanza
`FirebaseAuthException(code: 'account-exists-with-different-credential')`. Hay que traducirlo, no
dejarlo escapar crudo.

**Efecto colateral útil:** las cuentas de Google llegan con `email_verified: true`, lo que encaja con
el endurecimiento del bootstrap del plan 11-07 (que exige correo verificado).

**Frontera honesta de la cobertura automatizada.** `firebase_auth_mocks` no modela `signInWithCredential`,
`signInWithPopup` ni el plugin de Google (que necesita canales de plataforma inexistentes en
`flutter test`). Lo que SÍ es testeable en `flutter test`, y por tanto lo único que este plan promete:
la lógica de post-ingreso (creación del espejo, idempotencia, nombre desde displayName), la traducción
de errores y el renderizado/estado del botón — todo ello a través de una costura inyectable. El
handshake real con Google queda para el runbook E2E del plan 11-15. Prohibido inventar cobertura del
handshake con un mock del propio plugin.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Google Identity → Firebase Auth | El idToken de Google se canjea por una sesión de Firebase |
| usuario de Google → `usuarios/{uid}` | Un proveedor federado nuevo escribe en la colección de perfiles |
| repo → pub.dev | Dependencia nueva en el binario de producción de la app cliente |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-17-01 | Elevation of Privilege | espejo `usuarios/{uid}` escrito por un usuario de Google | mitigate | La regla vigente ya fuerza `role == 'cliente'` y `restauranteId == null` para cualquier auto-creación, y no se toca. Test explícito sobre el mapa escrito, y la suite de rules de `usuarios` (plan 11-04) cubre el intento de auto-ascenso |
| T-11-17-02 | Spoofing | idToken de Google falsificado o de otra app | mitigate | El canje lo hace Firebase Auth con `signInWithCredential`; el `serverClientId` (Web client ID del proyecto) ata el token a este proyecto. Un client ID equivocado produce idToken nulo, y el adaptador lo convierte en un error explícito en vez de continuar |
| T-11-17-03 | Spoofing | toma de una cuenta existente de email/contraseña vía Google | mitigate | Firebase devuelve `account-exists-with-different-credential` y NO fusiona cuentas automáticamente; se traduce a un mensaje que obliga a entrar con contraseña primero. Caso de test dedicado |
