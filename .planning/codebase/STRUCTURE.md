## Directory Purposes

**`app_cliente/lib/core/` and `panel_admin/lib/core/`:**
- Purpose: Cross-cutting infrastructure shared by all features within that app
- Contains: `firebase_bootstrap.dart` (init + emulator wiring), `firebase_providers.dart` (Riverpod DI seam for `FirebaseAuth`/`FirebaseFirestore` — tests override these instead of touching `FirebaseX.instance`), `state_machines.dart` (pure Dart transition tables, UI-only), `format.dart` (currency/date formatting), `theme.dart`
- Key files: `app_cliente/lib/core/tx_mutex.dart` exists only in `app_cliente` (client-side write serialization for reservas/sesiones/pedidos/calificaciones — `panel_admin` does not need it because staff mutations are simpler single-field updates)

**`{app}/lib/features/<feature>/`:**
- Purpose: One vertical slice per user-facing capability; each contains its own screen(s), Riverpod controller/provider, and (for panel_admin CRUD features) form dialogs
- Convention: `<feature>_screen.dart` (widget tree), `<feature>_controller.dart` or `<feature>_provider.dart` (state + Firestore calls), matching `.g.dart` generated by `riverpod_generator`

**`{app}/lib/models/`:**
- Purpose: Immutable `freezed` DTOs, one Dart file per Firestore document shape (plus generated `.freezed.dart`/`.g.dart`)
- Convention: every model implements `factory X.fromDoc(DocumentSnapshot<Map<String, dynamic>> doc)` as the canonical constructor from Firestore; `fromJson` factories are dead code inherited from the pre-Firebase REST era — do not extend them, use `fromDoc`
- `panel_admin` has staff-only variants of some models with `_staff` suffix (e.g. `categoria_staff.dart`, `pedido_staff.dart`, `producto_staff.dart`) that carry additional fields/behavior not exposed to `app_cliente`

**`backend/`:**
- Purpose: Historical reference only — the FastAPI+MySQL implementation that predates the Phase 10 Firebase migration
- Generated: no (hand-written), but not part of the live system
- Committed: yes, intentionally retained
- Do not add new features here; do not wire either Flutter app to it

**`scripts/`:**
- Purpose: Node.js Admin-SDK operational tooling (seed, and via `firebase-tools`, emulator/deploy commands)
- Generated: `scripts/node_modules/` is generated (gitignored); `scripts/serviceAccountKey.json` (if present) is a gitignored SECRET, never commit it
- Committed: `scripts/seed_firebase.mjs`, `scripts/package.json` yes; generated/secret files no

## Key File Locations

**Entry Points:**
- `app_cliente/lib/main.dart`: mobile app entrypoint (calls `bootstrap()` then `runApp(GriApp)`)
- `panel_admin/lib/main.dart`: web app entrypoint (same pattern)
- `scripts/seed_firebase.mjs`: manual bootstrap/seed entrypoint (Admin SDK, run via `node scripts/seed_firebase.mjs`)

**Configuration:**
- `firebase.json` (repo root): Firestore rules/indexes file paths + emulator ports (auth 9099, firestore 8080, UI 4000)
- `{app}/lib/firebase_options.dart`: per-app Firebase project config, generated by `flutterfire configure` (fallback: manual literal values documented in `docs/FIREBASE_SETUP.md` §7)
- `{app}/pubspec.yaml`: dependency pins — `firebase_core 4.13.0`, `firebase_auth 6.5.7`, `cloud_firestore 6.8.0` are LOCKED identical across both apps

**Core Logic (authorization/business rules):**
- `firestore.rules` (repo root): the actual "backend" — every authorization decision and state-machine enforcement lives here
- `firestore.indexes.json` (repo root): composite indexes required by tenant/staff-scoped queries
- `{app}/lib/core/state_machines.dart`: client-side (advisory only) mirror of the transition tables enforced in `firestore.rules`

**Testing:**
- `app_cliente/test/`, `panel_admin/test/`: directory structure mirrors `lib/features/*`, plus a top-level `state_machines_test.dart` per app and a shared `test/helpers/` for fakes/mocks

## Naming Conventions

**Files:**
- Screens: `<feature>_screen.dart` (e.g. `menu_mesa_screen.dart`, `dashboard_screen.dart`)
- Controllers (imperative actions, mutations): `<feature>_controller.dart` (e.g. `auth_controller.dart`, `reserva_controller.dart`)
- Providers (data reads/streams): `<feature>_provider.dart` (e.g. `pedidos_provider.dart`, `mesas_provider.dart`)
- Generated Riverpod code: `<file>.g.dart` (never hand-edit; regenerate with `build_runner`)
- Generated freezed code: `<model>.freezed.dart` + `<model>.g.dart`
- Form dialogs (panel_admin CRUD): `<entity>_form_dialog.dart` (e.g. `mesa_form_dialog.dart`, `producto_form_dialog.dart`)

**Directories:**
- One directory per feature under `lib/features/`, lowercase snake_case matching the domain concept in Spanish (`pedidos`, `reservas`, `sesion_qr`, `configuracion`)
- Widgets specific to one feature that aren't full screens live in a `widgets/` subdirectory of that feature (e.g. `panel_admin/lib/features/dashboard/widgets/mesa_tile.dart`)

## Where to Add New Code

**New client-facing feature (app_cliente):**
- Screen + controller/provider: `app_cliente/lib/features/<new_feature>/`
- Model (if a new Firestore shape): `app_cliente/lib/models/<entity>.dart` with a `fromDoc` factory
- Route registration: `app_cliente/lib/app.dart` (add to the 4-tab `StatefulShellRoute` or as a pushed full-screen route depending on whether it needs the bottom nav)
- Authorization: add/extend the relevant `match` block in `firestore.rules` FIRST — the Dart state machine tables are advisory only
- Tests: `app_cliente/test/<new_feature>/`

**New staff-facing feature (panel_admin):**
- Screen + provider: `panel_admin/lib/features/<new_feature>/`
- Route registration: `panel_admin/lib/app.dart` (add to the single `ShellRoute`, plus a sidebar entry in `panel_admin/lib/features/shared/app_shell.dart`)
- Authorization: extend `firestore.rules` (likely reusing `staffOf()`/`menuStaffOf()`/`cocinaStaffOf()` helpers)
- Tests: `panel_admin/test/<new_feature>/`

**New Firestore collection:**
1. Define the doc shape and ID convention (auto-id vs. deterministic — see ARCHITECTURE.md Data Model table for existing conventions to follow)
2. Add a `match /collection/{id}` block to `firestore.rules`, respecting the documented access-call budget (`firestore.rules:12-18`)
3. Add any required composite index to `firestore.indexes.json`
4. Add the model (`fromDoc` factory) in both apps' `lib/models/` if both need it, or just the relevant app
5. If seed/demo data is needed, extend `scripts/seed_firebase.mjs`

**Restaurant/staff onboarding (currently NOT self-service):**
- There is no in-app "create restaurant" or "invite staff" flow. To add one, either (a) extend `panel_admin/lib/features/configuracion/` with a super_admin-only creation UI plus corresponding `allow create` support already present in `firestore.rules:88` for `restaurantes` (staff invitation would still require a privileged claims-writing mechanism — Cloud Functions or an Admin SDK-backed callable, since client SDKs cannot set custom claims), or (b) continue operating via `scripts/seed_firebase.mjs` extensions. See ARCHITECTURE.md "Bootstrap Path" section before planning any related phase.

**Shared/cross-app logic:**
- Utilities that both apps need are currently duplicated (not shared via a package) — e.g. `state_machines.dart`, `firebase_bootstrap.dart`, `authErrorMessage()` exist as near-identical copies in both `app_cliente/lib/core/` and `panel_admin/lib/core/` (or `features/auth/`). If a shared package is introduced later, this is the logic to extract first.
