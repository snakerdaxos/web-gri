# Coding Conventions

**Analysis Date:** 2026-08-19

**Scope:** This document covers the two active Flutter clients — `app_cliente/` (mobile client) and `panel_admin/` (Flutter Web admin panel) — plus the Firebase surface they share at the repo root (`firestore.rules`, `firestore.indexes.json`, `scripts/seed_firebase.mjs`). The `backend/` directory is an ARCHIVED FastAPI+MySQL implementation kept only as historical reference; its Python conventions are NOT current and are not described here. Where the Dart code is explicitly a "port" of the old Python backend (state machines, seed data shapes), that lineage is noted but the Dart code is the one to follow.

Both apps are structurally near-identical (same `lib/core/`, `lib/features/<name>/`, `lib/models/` layout; same pubspec dependency versions "LOCKED" between them per code comments) — conventions below apply to both unless stated otherwise.

## Naming Patterns

**Files:**
- `snake_case.dart` throughout — e.g. `menu_mesa_screen.dart`, `pedidos_provider.dart`, `firebase_providers.dart`.
- Generated files sit next to their source with fixed suffixes: `*.freezed.dart` (freezed), `*.g.dart` (json_serializable / riverpod_generator). Never hand-edit these — they're regenerated by `build_runner`.
- Screens: `<feature>_screen.dart` (e.g. `cocina_screen.dart`, `mesas_screen.dart`, `reserva_wizard_screen.dart`).
- Providers/controllers: `<feature>_provider.dart` or `<feature>_controller.dart` (e.g. `pedidos_provider.dart`, `carrito_controller.dart`, `auth_controller.dart`). A file often contains both plain function providers and a `@riverpod class ...Controller` in the same file when they're tightly coupled to one feature (see `features/pedidos/pedidos_provider.dart`).
- Test files: `<thing>_test.dart` mirroring the feature under test, under `test/<feature>/`.

**Functions:**
- `camelCase`, Spanish domain verbs for actions: `crearPedido`, `solicitarCuenta`, `abrirSesion`, `entregarCuenta`, `validarTransicion`, `puedeTransicionar`, `transicionesDe`.
- Private helpers/implementation details prefixed `_` (e.g. `_crearPedido` wraps the public `crearPedido` to add a mutex — see Function Design below).
- Riverpod-generated provider functions are plain top-level functions annotated `@riverpod` (function name becomes `<name>Provider`, PascalCase class becomes `<Name>Provider` for notifiers).

**Variables:**
- `camelCase`. Domain nouns are Spanish (`mesaId`, `restauranteId`, `usuarioId`, `cuentaSolicitada`, `sesionId`). English is used only for Flutter/Dart/Firebase SDK types and generic infra (`db`, `ref`, `snap`, `tester`).
- IDs that mirror Firestore doc IDs keep the `Id` suffix explicitly typed `String` (Firestore doc IDs, not ints) — e.g. `restauranteId`, `mesaId`, `categoriaId`, `productoId`.

**Types:**
- `PascalCase` for classes/models: `Pedido`, `PedidoItem`, `RestauranteDetalle`, `SesionMesa`.
- Freezed model classes are declared `abstract class X with _$X` (freezed 3.x abstract-class style, not the old `@freezed class X with _$X`).
- Domain exceptions are named `<Domain>Exception` (`PedidoException`) or reuse Dart's built-in `StateError`/`ArgumentError` for validation/state failures (see Error Handling below) — there is no single custom exception hierarchy.
- Riverpod-generated stream/future typedefs follow SDK convention: `Stream<T>`, `Future<T>`, `AsyncValue<T>`.

## Code Style

**Formatting:**
- Standard `dart format` conventions (no custom `.dart_format` config found). 2-space indent, trailing commas used to force multi-line argument lists (idiomatic Flutter).

**Linting:**
- `analysis_options.yaml` (both apps, identical): `include: package:flutter_lints/flutter.yaml` plus one added rule: `avoid_print: true`.
- `riverpod_lint` + `custom_lint` are explicitly and intentionally OFF in both apps — comment in both `analysis_options.yaml` files states the published `custom_lint`/`riverpod_lint` pairing is incompatible with the pinned `riverpod` 3.3.x+ line (see `04-02-SUMMARY.md`). Do not attempt to re-add these without checking version compatibility first.
- Analyzer excludes generated/platform folders: `build/**`, `android/**`, `ios/**`, `web/**`, `windows/**`, `macos/**`, `linux/**`.
- `avoid_print` is enforced — use `debugPrint` for dev-only diagnostics (see `app_cliente/lib/features/pedidos/menu_mesa_screen.dart` catch-all handler using `debugPrint('enviar pedido falló: $e')`).

## Import Organization

**Order (observed convention, not enforced by a lint rule):**
1. `dart:` core imports (e.g. `dart:async`)
2. `package:` imports — Flutter/Firebase/Riverpod/go_router SDKs, alphabetically-ish grouped by package
3. Relative project imports (`../../core/...`, `../sesion_qr/...`, `./carrito_controller.dart`), generally core → sibling feature → same-feature file
4. `part 'x.freezed.dart'; part 'x.g.dart';` declarations always come immediately after imports, before any class.

**Path Aliases:**
- None. All intra-package imports are relative (`../../core/firebase_providers.dart`), consistent with a two-app (not monorepo-package) structure. Cross-package imports don't exist — `app_cliente` and `panel_admin` are fully independent Flutter projects with duplicated core/model code, not a shared package.

## Firebase / Provider Architecture Convention (critical, cross-cutting)

Both apps enforce one hard rule, stated explicitly in code comments (`core/firebase_providers.dart`, `test/helpers/firebase_fakes.dart`):

> **Features NEVER touch `FirebaseAuth.instance` / `FirebaseFirestore.instance` directly.** They always read `firebaseAuthProvider` / `firestoreProvider` from `lib/core/firebase_providers.dart`. Only `firebase_providers.dart` and `firebase_bootstrap.dart` touch the singletons.

This is what makes the fake-based test suite possible (see TESTING.md) — tests override `firebaseAuthProvider`/`firestoreProvider` with `MockFirebaseAuth`/`FakeFirebaseFirestore` and the entire app is cut off from the real backend with zero code changes.

```dart
// lib/core/firebase_providers.dart
@Riverpod(keepAlive: true)
FirebaseAuth firebaseAuth(Ref ref) => FirebaseAuth.instance;

@Riverpod(keepAlive: true)
FirebaseFirestore firestore(Ref ref) => FirebaseFirestore.instance;
```

When adding new Firestore/Auth access, inject via `ref.watch(firestoreProvider)` / `ref.read(firebaseAuthProvider)` — never `FirebaseFirestore.instance` inline in a feature file.

## Riverpod Provider Conventions

- Uses `riverpod_generator` (`@riverpod` / `@Riverpod(keepAlive: true)` annotations), NOT the legacy manual `StateNotifierProvider`/`Provider(...)` boilerplate style, except for one hand-written top-level `Provider<GoRouter>` per app (`app.dart`) — router providers are not code-generated because they need `ref.listen` wiring at construction time.
- `keepAlive: true` is used for app-wide singletons that must survive navigation: `firebaseAuthProvider`, `firestoreProvider`, `authStateChangesProvider`/`authStateProvider`. Feature-scoped providers (cart, pedidos stream, staff providers) are left auto-dispose (default).
- Mutation controllers follow this shape:
  ```dart
  @riverpod
  class PedidosController extends _$PedidosController {
    @override
    FutureOr<void> build() {}

    Future<String> enviar() async {
      state = const AsyncLoading<void>();
      try {
        // ... perform mutation, return result ...
      } finally {
        state = const AsyncData<void>(null);
      }
    }
  }
  ```
  Controllers built this way expose `FutureOr<void> build()` (no meaningful state to hold) and communicate outcome via the return value of the mutation method + thrown domain exceptions, not via `state`. `state` is only used to drive a `isLoading` UI flag through `AsyncLoading`/`AsyncData`.
- Read-only live data is exposed as `@riverpod Stream<T> ...(Ref ref)` functions wrapping `.snapshots()` queries — see `pedidosSession` in `app_cliente/lib/features/pedidos/pedidos_provider.dart`. Client-side transforms (e.g. `.reversed`) are applied in the `.map()` when Firestore doesn't have the matching composite index for server-side ordering — always document why in a comment when doing this (see existing example).
- Family providers use record/positional syntax typical of `@riverpod` (e.g. `restauranteDetalleProvider('demo')` seen in tests) — parameters map straight to the generated function signature.
- Auth claims are exposed via a `claims` provider returning a Dart record `({String role, String? rid})`, not a class — the whole app treats `{role, rid}` as the sole authorization signal (mirrors the Firestore custom-claims shape 1:1). Tests override this provider directly instead of mocking ID tokens: `claimsProvider.overrideWith((ref) async => (role: 'mesero', rid: 'demo'))`.

## freezed / json_serializable Model Conventions

- Declared as `@freezed abstract class X with _$X { const factory X({...}) = _X; ... const X._(); }` — the private unnamed constructor `const X._()` is added whenever the model needs computed getters/extensions on top of the generated fields (e.g. `Pedido.codigoCorto`).
- Every Firestore-backed model has a canonical `factory X.fromDoc(DocumentSnapshot<Map<String, dynamic>> doc)` constructor that is the ONLY sanctioned way to build the model from Firestore. It reads `doc.data()`, defensively casts each field with `as T? ?? default`, and converts `Timestamp` → `DateTime` via `.toDate()`.
- `fromJson`/`toJson` (json_serializable) are still generated on most models but are explicitly documented as **dead code inherited from the old REST era** — see comment in `pedido.dart`: `/// 'fromJson' heredado de la era REST — sin uso tras la migración; la vía canónica es [fromDoc].` Do not build new features around `fromJson` for Firestore-sourced data; use `fromDoc`.
- DTOs that never round-trip through Firestore (e.g. `ReservaCreate`, a wizard input DTO) skip `fromDoc` entirely and only keep `fromJson`/`toJson` — same "dead code" caveat applies, they're just not deleted.
- Money fields are always `int` (COP, no floats/doubles) — explicitly called out in comments as an anti-pattern to avoid (`'total' is int` / `// int COP — sin floats (research anti-pattern)`). New models with prices must follow this.
- Domain enums (`estado`) are modeled as plain `String`, not Dart `enum`, specifically because they cross the Firestore wire as strings and must match `firestore.rules` string literals exactly — see `core/state_machines.dart` header comment. UI presentation (label/color) for a state string lives in an `extension XEstadoX on X` block using `switch (estado) { 'valor' => ..., _ => fallback }` exhaustive-with-fallback pattern (see `PedidoEstadoX` in `pedido.dart`).
- `freezed` is version-pinned to a prerelease (`4.0.0-dev.3`) in both pubspecs — a documented, deliberate pin (3.2.6-dev.1 generates invalid `required final List<T>` for List fields). Do not bump freezed without checking this note in `pubspec.yaml`.

## go_router Routing Conventions

- One `goRouterProvider` (`Provider<GoRouter>`) per app in `lib/app.dart`, built by hand (not generated).
- Auth guard pattern (identical in both apps): a `ValueNotifier<int> routerNotifier` is bumped via `ref.listen(authStateProvider/authStateChangesProvider, ...)` and passed as `refreshListenable`; the `redirect` callback reads `ref.read(authStateProvider).value` (NOT `.watch`, to avoid rebuilding the router itself) and treats anything other than `AsyncData` with a non-null `User` as "logged out" — `isLoading` (session restoring) and `AsyncError` both count as not-logged-in.
- **app_cliente** uses `StatefulShellRoute.indexedStack` for the 4-tab bottom nav (Inicio/Restaurantes/Reservas/Perfil) — each branch preserves its own scroll/data state across tab switches. Full-screen pushes (QR scan, mesa menu, reservation wizard, restaurant detail) are declared as top-level `GoRoute`s OUTSIDE the shell so they cover the bottom nav.
- **panel_admin** uses a single `ShellRoute` (persistent sidebar) since the admin only ever has one active branch — `AppShell(location: state.uri.path, child: child)` derives the highlighted sidebar item from the current path rather than from shell branch index.
- Route paths are short, Spanish, lower-kebab/plain-segment (`/mesa`, `/mesa/pedidos`, `/reservas/wizard`, `/restaurantes/:id`), never English feature names.
- Path parameters are always `String` end-to-end (Firestore doc IDs/slugs, not ints) — e.g. `state.pathParameters['id']!` for a restaurant slug.
- Query parameters are used for optional/display-only data passed between screens (`state.uri.queryParameters['restauranteNombre']`), not for anything requiring validation.

## Error Handling

- **Domain-level errors** (business rule violations meant to surface to the end user) are thrown as small custom `Exception` classes carrying a ready-to-display `message` string — e.g. `PedidoException('Tu carrito está vacío')`. The convention is: the exception's `message`/`toString()` IS the user-facing copy, already in Spanish, already correctly worded — UI code shows it verbatim in a `SnackBar`, no further mapping needed.
- **Programmer/state errors** (should-never-happen / race-lost conditions) use Dart's built-in `StateError` (e.g. `entregarCuenta` throws `StateError('...ya no está activa')` when a race is lost) and `ArgumentError`/`ArgumentError.value` for local input validation before any network call (e.g. email/password format checks in `LoginController.submit`, unknown state-machine name in `transicionesDe`).
- **Firebase SDK errors** (`FirebaseAuthException`) are translated to Spanish user messages via a single shared mapping function per app — `authErrorMessage(FirebaseAuthException e, {required String fallback})` in `features/auth/auth_controller.dart` — switching on `e.code` (`invalid-credential`, `network-request-failed`, `too-many-requests`, `invalid-email`, `email-already-in-use`, `weak-password`, default fallback). New Firebase Auth call sites should route errors through this helper rather than inventing new message text.
- **Screen-level catch pattern** (repeated across features): catch the specific domain exception first for a precise message, then a catch-all for anything else mapped to a generic "connection error" message, always guarded by `if (!mounted) return;` before touching `context`/`setState`:
  ```dart
  try {
    await ref.read(pedidosControllerProvider.notifier).enviar();
    widget.onEnviado();
  } on PedidoException catch (e) {
    if (!mounted) return;
    ScaffoldMessenger.of(context).showSnackBar(SnackBar(content: Text(e.message), ...));
  } catch (e) {
    debugPrint('enviar pedido falló: $e');
    if (!mounted) return;
    ScaffoldMessenger.of(context).showSnackBar(const SnackBar(content: Text('Error de conexión. Intenta de nuevo.'), ...));
  }
  ```
- **Anti-spoofing / server-trust pattern:** critical writes (creating a pedido, requesting the bill) are wrapped in `db.runTransaction(...)` and re-validate ownership/state INSIDE the transaction (re-reading the session doc and checking `usuarioId == uid` and `estado == 'activa'`) even though `firestore.rules` also enforces this — the client-side check exists purely to fail fast with a friendly message before the rules reject the write. Do not treat client-side checks as the security boundary; `firestore.rules` is the actual authorization boundary (see ARCHITECTURE.md / firestore.rules for the rule definitions).
- Concurrency guard: a small in-process mutex helper `seccionCritica()` (`lib/core/tx_mutex.dart`) wraps sensitive transaction call sites to serialize double-taps from the same client before they even reach Firestore's OCC (optimistic concurrency control).

## Logging

**Framework:** None (no `logger`/`structlog` equivalent). `debugPrint` only, and only for dev-time diagnostics after a genuinely unexpected error is already being shown to the user via SnackBar. `avoid_print` lint forbids bare `print`.

**Patterns:**
- Log the exception right before surfacing the generic fallback message to the user: `debugPrint('enviar pedido falló: $e');` — never log and silently swallow without also informing the user.

## Comments

**When to Comment:**
- Comments are dense and used deliberately to record: (1) WHY a design decision was made (often referencing a phase/plan number, e.g. "Phase 10", "MIGRA-06", "Pitfall 2 del research 10"), (2) the Firestore doc shape a model/query depends on, and (3) explicit call-outs of intentional deviations from an "obvious" implementation (e.g. why `fromJson` is dead code, why ordering is done client-side, why a version is pinned to a prerelease).
- File-level header comments explain the file's role and its relationship to `firestore.rules` or to the archived Python backend it was ported from (e.g. `core/state_machines.dart`: "port 1:1 de backend/app/core/state_machines.py").
- Doc-comments (`///`) are used on public functions/classes to describe transactional steps as a numbered list matching the actual `runTransaction` steps in the body — keep this in sync when editing transaction logic.

**JSDoc/TSDoc equivalent (Dartdoc):**
- `///` triple-slash Dartdoc comments on all public classes, top-level functions, and non-trivial provider functions. Regular `//` for inline implementation notes.

## Function Design

**Size:** Small, single-purpose. Transactional mutations are commonly split into a public wrapper (does cheap pre-checks + wraps in the mutex/loading state) and a private `_` implementation that does the actual `runTransaction` — e.g. `crearPedido` (public, checks empty cart, calls `seccionCritica`) → `_crearPedido` (private, the real transaction).

**Parameters:** Firestore/Auth instances (`FirebaseFirestore db`, `FirebaseAuth auth`) are passed as the FIRST positional parameter into standalone domain functions (not read from a provider inside the function) — this is what makes them trivially testable with a `FakeFirebaseFirestore` without a `ProviderContainer`. Everything else is named parameters with `required` where there's no sensible default.

**Return Values:** Mutations that create a document return the new doc's `id` (`Future<String>`). Mutations that only update return `Future<void>`. Domain validation functions return `bool` (`puedeTransicionar`) or throw (`validarTransicion`) as two flavors of the same check — callers pick whichever fits (guard vs. hard-fail).

## Module Design

**Exports:** No barrel files (`index.dart`/library-export aggregators) — every file is imported individually by its concrete path. This is consistent with the "no path aliases" convention above.

**Feature module shape:** Each `lib/features/<name>/` directory typically contains: one or more `*_screen.dart` (UI), one `*_provider.dart` and/or `*_controller.dart` (state + Firestore access), and optionally a `widgets/` subdirectory for extracted, reusable pieces of that feature only (e.g. `panel_admin/lib/features/cocina/widgets/pedido_card.dart`). Models are NOT nested under `features/` — they live centrally in `lib/models/`, shared across features within the same app.

**Cross-app duplication:** `app_cliente` and `panel_admin` do not share a package. Core infra (`firebase_providers.dart`, `firebase_bootstrap.dart`, `state_machines.dart`, `format.dart`, `theme.dart`) and any model that both apps need (`user.dart`, `restaurante.dart`, `reserva.dart`) are duplicated file-for-file between the two `lib/core/` and `lib/models/` trees, kept in sync by convention/code review, not by a shared package. When changing shared logic (e.g. `state_machines.dart`), apply the same change to both `app_cliente/lib/core/` and `panel_admin/lib/core/`.
